Isochronous transfers, 2026-11-15

Scope
  USB devices that carry a timed stream (USB sound devices, webcams) use
  isochronous transfers. The controller driver had none: such an endpoint
  could not be configured and URB_FUNCTION_ISOCH_TRANSFER was refused. This
  adds them to the controller driver. It does not add a sound or camera
  driver: ReactOS 0.4.16 builds and ships no USB audio class driver (its
  drivers/usb/usbaudio is not in the build and has no INF), has no USB video
  class driver, and its own USB stack leaves isochronous unimplemented. Until
  a class driver exists nothing in ReactOS issues these transfers.
  (Later the same day ReactOS's own usbaudio driver was repaired to do so:
  evidence/usb-sound.txt.)

Controller driver
  - Endpoint context: type 1 (OUT) or 5 (IN), no retries, interval as an
    exponent of 125 microseconds (bInterval - 1, plus 3 at full speed), Max
    Burst from the additional transactions (high speed) or the companion
    (SuperSpeed, with Mult), Max ESIT Payload from the packet size or the
    companion's wBytesPerInterval. src/core/usb_policy.cpp.
  - One packet is one TD of one Isoch TRB with Start Isoch ASAP, interrupt
    on completion and, for all but a request's last packet, Block Event
    Interrupt. Transfer Burst Count and Last Burst Packet Count follow xHCI
    4.11.2.3. Packet data is placed in the common buffer so that no packet
    crosses a 64 KiB boundary. src/core/isoch.cpp.
  - Several requests share an endpoint ring. Each ring entry maps to its
    request and packet; a transfer event settles that packet, and any older
    entry that got no event of its own is reported as not accessed (Missed
    Service). Ring underrun and overrun events are ignored.
    src/reactos/isoch.cpp.
  - One service thread per bus, created when an isochronous endpoint is first
    configured, takes requests in arrival order, puts them on the ring when
    there is room, collects finished ones at PASSIVE_LEVEL (copying received
    data out and writing each packet's status and length) and completes
    them. It stops the endpoint when one of its requests is cancelled or has
    had no answer for five seconds. src/reactos/usb_isoch.cpp.
  - Selecting a setting, URB_FUNCTION_ABORT_PIPE, device removal and
    controller stop end every request queued on the endpoint through a real
    Stop Endpoint and dequeue move.
  - URB_FUNCTION_GET_CURRENT_FRAME_NUMBER returns the controller's 11-bit
    frame index. StartFrame is written with the frame a request was queued
    in; a start frame chosen by the caller is not honoured.
  - A pipe's MaximumPacketSize reports what one service interval carries.
  Control, bulk and interrupt transfers keep their existing path.

Host checks
  Nine suites pass with address and undefined-behaviour sanitizers; the new
  one (tests/isoch_tests.cpp, 562 checks) covers endpoint contexts at full,
  high and SuperSpeed, TRB encoding including burst counts, placement
  against 64 KiB boundaries, capacity bounds and event decoding.

Emulator, QEMU/KVM, ReactOS USB-root image, one qemu-xhci controller, system
disk as USB storage, QEMU usb-audio (full speed, one isochronous OUT endpoint,
192 bytes every frame) on a root port. A test client (tests/isoch, built only
with XHCI_NATIVE_ISOCH_TEST, never delivered) binds to the device, keeps four
requests of ten packets queued and resubmits each from its completion. Left
channel carries the running sample number and right its complement, so the
packets QEMU captured at the device (pcap=) show any loss or reordering. The
controller driver was a delivery build with the untested-controller switch on.
  1. Stream: 300 requests, 3000 packets, all reported successful, in 2.999 s.
     Capture: 3000 packets of 192 bytes, largest gap 1.12 ms, 144000 samples
     in sequence, no right-channel mismatch.
  2. Drop: four queued requests, then the idle setting selected. All four
     returned USBD_STATUS_CANCELED; none reached the device.
  3. Cancel: streaming again, the newest queued request cancelled. Three
     requests returned cancelled, the 21 before them complete.
  4. Restart: 100 further requests, 1000 packets, all successful in 0.99 s.
     Capture over 2 to 4: the only sequence breaks are the 40 dropped and
     30 cancelled packets.
  5. Timer service (fixture XHCI_TEST_NO_INTERRUPT, no interrupt delivered):
     phases 1 to 4 with the same results; 11987 polled batches, no fault.
  6. Unplug: a 20 s stream, device removed after 10.8 s. 10781 packets
     captured in sequence, the four requests then queued returned cancelled,
     the client's next requests were refused, ReactOS kept running and shut
     down normally.
  7. Load: a 20 s stream while a UAS disk on the same controller was read
     and written in a loop (checksums and written-file readback as before).
     20000 packets, none failed, none lost or reordered. The capture shows
     two to five gaps of 1.6 to 6 ms between packets; the ring held at least
     30 ms of packets throughout, so these are taken to be emulator timing,
     which this setup cannot separate from the driver.
  The committed source differs from the binary used in 1 to 4, 6 and 7 by
  formatting; the rebuilt file differs in seven bytes (time stamp, checksum
  and three source line numbers) and repeated 1 to 4 with the same results.

Both directions and the faster speeds, same day
  QEMU has no device with an isochronous IN endpoint and none above full
  speed, so tests/isoch/redir_device.py supplies one: a small program that
  speaks the usbredir protocol to QEMU's usb-redir device and presents a
  vendor-specific device with one isochronous OUT and one isochronous IN
  endpoint at full, high or SuperSpeed, with a chosen bInterval and payload
  per service interval. It checks every OUT packet against the client's
  counting pattern as it arrives and feeds the IN endpoint numbered packets
  (a four-byte packet number, then a byte ramp) at the endpoint's nominal
  rate, every tenth one 16 bytes short. The test client was extended to
  stream in both directions at once and to check each received packet's
  number, length and contents. Controller driver: the delivery build with
  the hub change of evidence/hub-enumeration.txt (sha256 c1c479e9...).
  Each row is one boot: a three-second run in both directions, then the
  drop, cancel and restart phases on both endpoints.

    speed  bInterval  bytes  packets/s  OUT at device        IN at client
    full       1        192     1000     3000 in 3.000 s      2939 + 61 empty
    high       4       1024     1000     3000 in 2.999 s      2879 + 121 empty
    high       1       1024     8000    24000 in 3.006 s     23519 + 481 empty
    high       1       3072     8000    24000 in 3.012 s     23519 + 481 empty
    super      1       1024     8000    24000 in 3.005 s     23938 + 62 empty
    super      3       3072     2000     6000 in 3.000 s      5980 + 20 empty
    super      4       6144     1000     3000 in 2.999 s      2984 + 16 empty

  In every row: no request and no packet reported failed in either
  direction; every OUT packet arrived whole, in order and at the full
  payload size, with no sequence break inside a run; every IN packet that
  carried data had the right contents and the next packet number, with
  lengths reported from payload - 16 to payload; the queued requests all
  came back when the setting was dropped, the cancelled request and those
  behind it returned cancelled, and both endpoints streamed again
  afterwards. The packet rates confirm the interval encoding at each speed.
  3072 bytes at high speed is three transactions per microframe; 3072 and
  6144 at SuperSpeed are bursts of three, the second with Mult 1.
  The empty IN packets are QEMU's: usb-redir keeps its own queue between
  the device program and the guest and answers with no data until that
  queue has filled (about 60 ms at the rate QEMU assumes), at the start of
  each run. The client counts them and they carry no error.
  The first SuperSpeed boots showed OUT packets out of order at the start
  of a run. That was the test client, which could resubmit a completed
  request before it had finished sending the first batch; it now hands
  requests over strictly in the order it filled them, and every row above
  is from the corrected client. QEMU's sound card passed again with it
  (3000 packets, every sample in sequence, same phases).

Not verified
  - Real hardware: nothing here has run on a controller that keeps real
    time. Missed Service, ring underrun, Block Event Interrupt and
    bandwidth errors as a real controller reports them are untested, and
    QEMU does not check the burst fields of an Isoch TRB (Transfer Burst
    Count, Last Burst Packet Count); those have host checks only.
  - Timing. The device program is paced by the host clock and QEMU's queue
    hides jitter in both directions, so these runs prove data, order,
    lengths and average rate, not that each packet met its interval.
  - Explicit start frames, and a device whose packets fail on the wire.
  - A device behind a high-speed or SuperSpeed hub. Behind QEMU's full-speed
    hub the sound-card test passes (evidence/hub-enumeration.txt).
  - Any class driver. ReactOS's usbaudio source compiles from the 0.4.16
    tree. In one boot it was registered for the sound card's audio function
    by registry entries alone, without an INF: ReactOS showed its New
    Hardware Wizard for "Audio Device", no audio class request reached the
    device and playing a sound file failed. Whether the driver loaded was
    not established; making it work is a task of its own.

Seen in passing
  One boot of the test image with the previous driver stopped on a ReactOS
  assertion (!Irp->CancelRoutine, with classpnp, mountmgr and fastfat on the
  stack) before any of this code was installed. Not reproduced, not
  investigated.
